# 插件管理

Meerkit 的监控能力由独立插件进程提供。管理页面可以导入、检查、信任、启用、禁用、导出和卸载插件，并查看进程日志与模块描述器。

## 导入方式

支持两种插件包格式：`.zip` 和 `.tar.gz`。

- 在“监控插件”页面上传包。
- 使用命令行 `meerkit plugin import <archive>`。
- 把包复制到 `${storage.data_dir}/plugins/inbox`，然后点击扫描或运行 `meerkit plugin scan`。

裸二进制、脚本目录和未知压缩格式不会被发现或执行。包解压有路径、文件数量、总大小和压缩比限制，并拒绝符号链接和重复路径。

## 安装校验

导入时会依次检查：

1. 清单字段、语义版本和协议范围。
2. 当前 OS/架构是否恰好有一个制品。
3. 制品路径、大小和 SHA-256 是否与清单一致。
4. 可选 Ed25519 签名是否覆盖当前清单与文档。
5. 同一插件 ID 与版本是否已经安装了不同内容。

导入成功不等于自动启用。启用时还会启动进程、执行标准 gRPC Health 和 Meerkit Health、在同一 gRPC 连接上建立 BrowserBridge Session、读取模块描述器并与清单核对。即使插件不调用浏览器能力，也使用同一个统一运行时注册空闲 Session。

## 信任状态

| 状态 | 含义 | 启用要求 |
| --- | --- | --- |
| `official` | 从正式发布包首次引导的官方插件 | 可直接启用 |
| `trusted` | 签名有效，公钥指纹已被信任 | 可直接启用 |
| `untrusted` | 签名有效，但发布者未知 | 核对并信任指纹 |
| `unsigned` | 没有签名 | 明确确认风险 |
| `development` | 开发宿主从源码构建 | 仅开发模式使用 |

信任身份是 Ed25519 公钥的 SHA-256 指纹，而不是清单中的 `vendor`、URL 或 key ID。签名能够检测包被篡改并关联发布密钥，但不能证明代码安全。

## 运行目录

默认插件状态位于 `${storage.data_dir}/plugins`：

```text
inbox/       待扫描的包
staging/     导入临时目录
packages/    保留的原始插件包
installed/   当前平台解出的制品
development/ 开发源码构建产物
rejected/    扫描失败的包
logs/        每个插件版本的进程日志
```

不要在运行期间手工修改 `packages/` 或 `installed/`。使用管理页或 CLI 保持数据库记录和文件一致。

## 启停与升级

- 同一个插件 ID 只会启用一个版本。
- 启用新版本时，宿主先健康检查和迁移监控配置，再替换旧模块和进程。
- 进程或协议启动失败会把插件标记为失败并保留错误详情。
- 禁用或卸载提供模块的插件后，已有监控仍保存在数据库中，但无法执行或编辑模块配置。
- 插件日志级别和格式在设置页修改；当前活动插件会重启以应用配置。
- 插件禁用、升级或退出会取消它拥有的浏览器请求与网络捕获。

## 第三方语言插件

第三方插件不需要使用 Go SDK。它必须实现公开的进程握手、gRPC 服务和 JSON 契约，并自行构建包中制品。宿主支持：

- `runtime.mode: direct`：直接执行制品，可附加固定参数。
- `runtime.mode: interpreter`：从宿主 `PATH` 查找解释器，并把 `{artifact}` 替换为制品路径。

宿主不会调用 shell，不展开变量或通配符。解释器及其兼容版本属于部署前置条件。详见[跨语言插件协议](/development/plugin-protocol)。

需要 Chrome 能力的插件还必须实现同一 gRPC Server 上的 BrowserBridge 双向流。浏览器目标、Action 和捕获模型见[浏览器自动化架构](/development/browser-automation)。
